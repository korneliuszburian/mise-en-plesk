# Production architecture research: mise-en-plesk

Date: 2026-08-18  
Scope: production-grade, SSH-only, read-only auditing of Plesk-hosted
WordPress on `master` and `dev`, Bitwarden Secure Notes credentials, bounded
scheduling, and Hermes Agent/WhatsApp alerts.

## Executive decision

The recommended production shape is a small, one-shot TypeScript process run
by a trusted Linux runner through a `systemd` service and timer:

```text
systemd timer
  -> one bounded scan process
      -> Bitwarden CLI session (runtime only)
      -> validated inventory
      -> fixed SSH command allowlist
      -> Plesk discovery + WordPress probes
      -> local vulnerability enrichment (and explicitly opt-in online enrichment)
      -> normalized findings/state
      -> atomic local outbox
      -> Hermes `send` adapter for P1 transitions
```

The Plesk control-plane APIs should be treated as optional adapters, not as the
baseline transport. Plesk REST is administrator-only; XML API is remote and
supports a broad set of operations, including operations that change state.
The current SSH path works with the available non-root accounts, keeps the
read-only boundary visible in one command allowlist, and also reaches the
filesystem and WP-CLI data that an API alone cannot provide. Plesk REST/XML
become useful later for metadata that is genuinely unavailable through the
approved SSH account, ideally over an explicitly approved SSH tunnel rather
than by opening a new public control-plane path.

This report records verified facts from first-party documentation and then
labels recommendations separately. It does not inspect or connect to any
Plesk server, Bitwarden vault, Hermes installation, or WhatsApp recipient.

## 1. Verified facts and their operational meaning

### 1.1 Plesk interfaces

#### Plesk CLI over SSH

Plesk documents Linux command-line utilities as tools for administering Plesk
objects. The `subscription` utility exposes `--list` and `--info` alongside
mutating commands such as `--create`, `--update`, and `--remove`. The `site`
utility similarly exposes `--list` and `--info`, while also exposing commands
that activate, suspend, update, or remove sites.

- [Plesk `subscription` CLI reference](https://docs.plesk.com/en-US/obsidian/cli-linux/using-command-line-utilities/subscription-subscriptions.37768/)
- [Plesk `site` CLI reference](https://docs.plesk.com/en-US/obsidian/cli-linux/using-command-line-utilities/site-sites.67067/)
- [Plesk CLI overview](https://docs.plesk.com/en-US/obsidian/cli-linux/using-command-line-utilities.40984/)

**Implication:** a remote shell account can be useful without giving the
scanner a general-purpose Plesk API client, but the executable must not accept
arbitrary Plesk arguments. The safe unit is a fixed, reviewed command such as
`plesk bin subscription --list`; the fact that a command-line utility also has
read/write operations is a reason for an allowlist, not permission to pass
through a user-supplied string.

Plesk's CLI references document human-oriented output and command semantics,
but do not establish a general JSON schema for every utility. **Recommendation:**
keep raw command output as evidence, parse only the documented read commands,
and maintain parser fixtures for each Plesk version encountered. Do not infer
that a successful `--list` proves that every filesystem candidate is a live
production site.

#### Plesk REST API

Plesk documents REST as an HTTP API at port `8443`, with JSON responses and an
OpenAPI description at `/api/v2/swagger.yml`. The documented HTTP method
semantics say that `GET` retrieves information and is read-only, while `POST`,
`PUT`, and `DELETE` create, update, and remove objects. The same reference says
that only the Plesk administrator can use REST API.

- [Plesk REST API overview](https://docs.plesk.com/en-US/obsidian/api-rpc/about-rest-api.79359/)

**Implication:** REST is attractive for structured Plesk inventory, but it does
not fit the current non-root baseline. It also does not replace SSH filesystem
access or WP-CLI. A future REST adapter must enforce `GET`-only methods and
endpoint allowlists; a generic REST method/path client would violate the
read-only design even if the first caller uses `GET`.

#### Plesk XML API

Plesk documents XML API as a remote procedure interface at
`https://<host>:8443/enterprise/control/agent.php`. Requests carry credentials
in HTTP headers and an XML operation packet in the body. The XML schemas list
different permissions per operator; for example, domain/site operations can
be available to administrator, reseller, or customer, while some server
operations are administrator-only. Plesk's server-information example uses a
`<server><get>...</get></server>` packet and can retrieve Plesk/OS versions,
resource statistics, updates, and administrator domain lists.

- [Plesk XML API overview](https://docs.plesk.com/en-US/obsidian/api-read-me-first/integration-and-automation-capabilities/xml-api-protocol.68677/)
- [XML API operator schemas and permissions](https://docs.plesk.com/en-US/obsidian/api-rpc/about-xml-api/reference/xml-schemas-for-xml-api-operators.58138/)
- [XML API server information request](https://docs.plesk.com/en-US/obsidian/api-rpc/about-xml-api/reference/managing-plesk-server/getting-server-information/request-packet-structure-and-samples.37024/)

**Implication:** XML can fill some inventory gaps for a lower-privileged Plesk
identity, but it is a large RPC surface and its protocol is not inherently
read-only. If adopted, model a small set of typed read packets and validate
the response against fixtures. Do not expose arbitrary XML, operator names, or
HTTP methods. The safer future transport is an SSH local port-forward to the
Plesk endpoint, provided that the operator explicitly approves that additional
path and the server account permits it; this is a recommendation, not a
property guaranteed by the Plesk docs.

### 1.2 OpenSSH client controls

The OpenSSH client reference documents the controls that matter for a batch
scanner:

- `BatchMode=yes` disables password prompts and host-key confirmation prompts
  intended for interactive use.
- `ConnectTimeout` bounds TCP connection and initial SSH handshake/key
  exchange; `ConnectionAttempts` bounds connection attempts.
- `StrictHostKeyChecking` controls handling of unknown or changed host keys.
- `ControlMaster`, `ControlPath`, and `ControlPersist` allow controlled
  connection reuse. The reference recommends that a control path include
  host/port/user (or `%C`) and live in a directory not writable by other users.
- `ForwardAgent` is disabled by default and the reference warns that agent
  forwarding should be enabled only with caution.

- [OpenBSD `ssh_config(5)`](https://man.openbsd.org/ssh_config)
- [Linux OpenSSH `ssh_config(5)`](https://man7.org/linux/man-pages/man5/ssh_config.5.html)

**Recommendation:** each scanner invocation should use a dedicated local
control-socket directory with restrictive permissions, `BatchMode=yes`, a
reviewed `UserKnownHostsFile`, `StrictHostKeyChecking=yes` after host keys are
enrolled, `ForwardAgent=no`, no X11 or TCP forwarding, a finite
`ConnectTimeout`, `ConnectionAttempts=1`, and a separate wall-clock/process
timeout. Control sockets should be closed and removed after the host batch;
`ControlPersist` must be finite rather than indefinite.

SSH-only here means that all Plesk and WordPress interaction is initiated as a
remote command over SSH. It does not automatically mean that a remote
`wp` command makes no outbound HTTP requests. Checks that consult
WordPress.org or a vulnerability service need an explicit network-egress
policy and a visible `external-enrichment` status.

### 1.3 systemd service and timer

The systemd timer reference states that a timer activates a matching service,
does not start a second instance while that service is already active, and can
store the last trigger time with `Persistent=true` to catch up after downtime.
`RandomizedDelaySec` spreads timer events to avoid workload spikes. Monotonic
settings such as `OnUnitActiveSec` express intervals relative to activation of
the triggered unit.

- [systemd timer unit reference](https://github.com/systemd/systemd/blob/main/man/systemd.timer.xml)

The systemd execution reference documents `NoNewPrivileges=true` as preventing
privilege gain through `execve`, and documents filesystem restrictions such as
`ProtectSystem=strict` and explicit `ReadWritePaths` allowlists. It also
documents private temporary directories and related namespace controls.

- [systemd execution and sandboxing reference](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml)
- [systemd service unit reference](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml)

**Recommendation:** deploy a dedicated non-root service account on a trusted,
always-on runner. Keep checkout/code immutable to the service and allow writes
only to a dedicated state directory containing inventory cache, finding state,
notification outbox/history, and reports. Use one short-lived scan process per
timer activation, `Persistent=true` for missed-run recovery, a bounded
`RandomizedDelaySec` for fleet spreading, and a local lock as a second line of
defence. Set explicit CPU/memory/task/output limits appropriate to the runner.
Do not let the service write into the source checkout, `$HOME` broadly, or
customer paths.

### 1.4 WP-CLI machine-readable probes and limits

The official WP-CLI command references support machine-readable output:

- `wp plugin list` supports `--format=json`, `--fields`, activation status,
  update status, `update_version`, `auto_update`, and optional WordPress.org
  fields including `wporg_status` and `wporg_last_updated`.
- `wp theme list` supports JSON and analogous status/update fields.
- `wp core check-update` queries the Version Check API and supports JSON plus
  selected fields.
- `wp core verify-checksums` compares installed core files with
  WordPress.org checksums and supports JSON output.
- `wp plugin verify-checksums --all --strict` verifies all installed plugins
  where WordPress.org checksums exist.
- `wp site list` supports JSON and exposes multisite site identity fields.

- [`wp plugin list`](https://developer.wordpress.org/cli/commands/plugin/list/)
- [`wp theme list`](https://developer.wordpress.org/cli/commands/theme/list/)
- [`wp core check-update`](https://developer.wordpress.org/cli/commands/core/check-update/)
- [`wp core verify-checksums`](https://developer.wordpress.org/cli/commands/core/verify-checksums/)
- [`wp plugin verify-checksums`](https://developer.wordpress.org/cli/commands/plugin/verify-checksums/)
- [`wp site list`](https://developer.wordpress.org/cli/commands/site/list/)

WP-CLI's own global parameters include `--path`, `--skip-plugins`,
`--skip-themes`, `--skip-packages`, and `--quiet`; its docs also list mutating
commands such as plugin/theme/core updates and database operations.

**Operational limitations:**

1. A WP-CLI command can fail while loading the site's PHP, plugin, theme, or
   database environment. That is an important health finding, not proof that
   SSH or the host is unreachable.
2. A checksum check is not a complete malware verdict. The official WP-CLI
   security guidance explains that WordPress.org may not have checksums for a
   premium or custom plugin; an unknown checksum must be reported as unknown,
   not safe or compromised.
3. `wp core check-update` and checksum commands may contact WordPress.org.
   They are SSH-transported probes, but not necessarily offline probes.
4. `--skip-plugins` or `--skip-themes` can make a command more resilient but
   changes what is being tested. Record the probe mode in the result.
5. Multisite needs explicit `wp site list` enumeration and per-site identity;
   one root-level plugin result is not automatically a complete network audit.

- [Official WP-CLI security checks guidance](https://developer.wordpress.org/news/2024/09/website-security-checks-wp-cli-for-site-owners-and-administrators/)

**Recommendation:** keep a fixed read-only WP-CLI probe profile. Parse JSON
from `plugin list`, `theme list`, `site list`, and `core check-update`; capture
exit code and bounded stderr; never use `wp eval` as a generic probe; never
include update/install/delete/database commands in the allowlist. Separate
local filesystem evidence (uploads PHP, executable files, timestamps) from
WP-CLI evidence and label confidence for each finding.

### 1.5 Bitwarden CLI, organization vaults, and Secure Notes

Bitwarden's official CLI documentation states that:

- the CLI must be connected to the correct Bitwarden server before login;
- login can use email/master password, API key, or SSO;
- API key or SSO login still requires a subsequent `bw unlock` to work with
  decrypted vault data in the normal case;
- unlock produces a session key, commonly exported as `BW_SESSION`;
- the session key is required for commands that touch vault data and is not
  persisted into a new terminal; `bw lock` or `bw logout` invalidates it;
- `bw list items --search` narrows item listing, `bw get item` retrieves one
  item, and `bw get notes` retrieves an item's note;
- Secure Notes are a distinct item type and use a Secure Note sub-template;
- organization items are accessed alongside the user's personal vault, with
  organization/collection permissions controlling visibility;
- users who join an organization using trusted devices cannot use the CLI to
  access data and should use an API key client secret for the authentication
  challenge.

- [Bitwarden Password Manager CLI](https://bitwarden.com/en-gb/help/cli/)
- [Bitwarden organizations](https://bitwarden.com/help/getting-started-organizations/)
- [Bitwarden vault synchronization](https://bitwarden.com/help/vault-sync/)

**Implication for this company setup:** being a member of an organization is
not equivalent to having a personal vault credential that the CLI can use.
The onboarding path must first establish the correct self-hosted/server
endpoint and an organization-permitted CLI authentication method. If the
operator has no API key/SSO path and the trusted-device restriction applies,
the scanner must fail preflight with instructions; it must not guess at a
personal vault or export the organization.

**Recommendation:** use `bw` only at runtime. Sync the vault before reading,
select exact Secure Note names or IDs, validate the note schema, and convert
the content directly into an in-memory credential descriptor. Never write
passwords to inventory, reports, outbox/history, command arguments, logs, or a
repo `.env`. For an always-on runner, prefer a dedicated least-privileged
organization identity and a short-lived session strategy owned by the runner
operator; the current interactive `BW_SESSION` helper is appropriate for
manual operation but is not by itself a production credential-rotation plan.

### 1.6 Hermes Agent and WhatsApp

Hermes' official CLI reference documents `hermes send --to <target> <message>`
as a one-shot send operation. It can reuse configured credentials and does not
require a running gateway for bot-token platforms including WhatsApp Cloud API.
The documented target format includes `whatsapp:<chat-id>`, and exit codes
distinguish success, delivery/backend failure, and usage errors. Hermes also
documents JSON output and a quiet mode for scripts.

- [Hermes CLI `send`](https://github.com/nousresearch/hermes-agent/blob/main/website/docs/reference/cli-commands.md)
- [Hermes script-output guidance](https://github.com/nousresearch/hermes-agent/blob/main/website/docs/guides/pipe-script-output.md)

Hermes' WhatsApp Cloud documentation states that outbound text is split at
4096-character chunks, that the current Cloud adapter supports direct messages
only in v1, and that Meta's default throughput is 80 messages/second per
business phone number while Hermes does not enforce that limit client-side.
The same documentation describes the need for Meta webhook configuration for
inbound gateway operation; that is separate from one-shot outbound sends.

- [Hermes WhatsApp Cloud guide](https://github.com/nousresearch/hermes-agent/blob/main/website/docs/user-guide/messaging/whatsapp-cloud.md)
- [Hermes environment variables](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/reference/environment-variables.md)

**Recommendation:** treat Hermes as a delivery adapter, never as scanner core.
Give it a single explicitly configured WhatsApp target, send only compact P1
state transitions, group events by host/site, and keep full reports local.
Validate the exact target before any test; use a separate guarded test command;
do not put Hermes session files or Meta credentials in the repository or in
Bitwarden SSH notes. Provider failure must leave the local outbox pending and
must not fail or mutate the remote scan.

Hermes' documented configuration uses local Hermes state such as
`~/.hermes/.env` and `~/.hermes/config.yaml`; that is convenient for a human
installation but should be mapped to a protected service account and a
separate secret provisioning mechanism for production. This is an operational
recommendation, not a claim that Hermes itself provides durable exactly-once
delivery. The scanner should assume at-least-once delivery and use stable
finding IDs, cooldowns, recovery events, and an outbox.

## 2. Options compared

| Boundary | Strengths | Weaknesses | Decision |
| --- | --- | --- | --- |
| Fixed Plesk CLI over SSH | Works with current access model; reaches filesystem and local binaries; obvious read-only allowlist | Human-oriented output; parsing/version fixtures required | **Baseline** |
| Plesk REST directly over HTTPS | JSON/OpenAPI; GET semantics are explicit | Administrator-only; new network/auth surface; no filesystem/WP-CLI access | Optional adapter, not baseline |
| Plesk XML directly over HTTPS | Rich typed operations and broader delegated permissions | RPC surface includes mutations; XML/auth/permissions complexity | Optional adapter, read packets only |
| Plesk REST/XML through SSH tunnel | Preserves an SSH-originated transport boundary while gaining API structure | More moving parts; still needs API credentials and endpoint allowlist | Future, only after explicit approval |
| WP-CLI over SSH | Native application context; rich JSON and checksum/update probes | Can load broken PHP; some probes use external WordPress.org services; custom plugins lack checksums | **Baseline application probe** |
| systemd timer + one-shot service | Native locking/scheduling, missed-run recovery, sandboxing, journal integration | Requires a trusted always-on runner and operational installation | **Recommended deployment** |
| cron | Available almost everywhere and simple | Weaker sandboxing/observability and less explicit overlap/missed-run semantics | Manual fallback only |
| Hermes `send` | Small subprocess boundary; direct outbound send; no gateway required for Cloud API | Provider credentials/state outside this repo; at-least-once caveat; direct-message/rate limits | **Recommended optional alert adapter** |

## 3. Recommended production architecture

### 3.1 Trust boundaries

1. **Credential boundary:** Bitwarden CLI returns a short-lived note value to
   memory. No downstream module receives the Bitwarden session key.
2. **Transport boundary:** the SSH executor accepts a typed host and a fixed
   command ID, not a shell string supplied by configuration. It disables
   forwarding and bounds time/output.
3. **Remote command boundary:** Plesk/WP/filesystem commands are an explicit
   read-only allowlist. `sudo` is allowed only for named fixed commands where
   the account needs it; never expose arbitrary `sudo` or arbitrary shell.
4. **Evidence boundary:** raw output is bounded and sanitized before reports;
   credentials, environment dumps, database values, and config secrets are
   never collected.
5. **State boundary:** finding state, cursor, reports, and notification outbox
   live under one protected local state directory. The source checkout is not
   a runtime database.
6. **Notification boundary:** the scanner emits typed finding transitions;
   Hermes only transports a redacted summary. Delivery failure cannot trigger
   a remote action.

### 3.2 Scan shape

Use a host-level pipeline with bounded concurrency rather than one unbounded
promise per subscription:

```text
preflight
  -> read exact Secure Notes
  -> validate host capabilities
  -> acquire per-run/per-host lock
  -> establish/reuse bounded SSH session
  -> collect host facts once
  -> enumerate subscriptions/candidates
  -> scan sites with per-host semaphore
  -> checkpoint cursor and findings after each bounded chunk
  -> reconcile transitions
  -> enqueue P1 notifications
  -> flush adapters
  -> emit report and health/heartbeat
```

Recommended controls are explicit `maxConcurrentHosts`,
`maxConcurrentSitesPerHost`, `maxSitesPerChunk`, SSH connect/command
timeouts, maximum stdout/stderr bytes, a cursor for host/site rotation, and
an overall run deadline. A failed site should become a typed health result and
not abort unrelated sites. A failed host should not silently resolve old
findings; mark the observation incomplete and let a stale-monitor policy
handle it.

### 3.3 Data contracts to preserve

Keep the existing top-level `AuditResult` compatibility, but make the durable
finding model the operational contract. Every finding should carry:

- stable ID derived from host + canonical site identity + signal;
- severity and lifecycle (`opened`, `reopened`, `resolved`);
- evidence and the exact probe/source that produced it;
- first/last seen and scan/cursor metadata;
- confidence/unknown state when a checksum, external API, or WP-CLI probe is
  unavailable;
- a bounded human action, never automatic remediation.

Persist state atomically and keep notification delivery at-least-once. A
provider acknowledgment should only mark the acknowledged event as delivered;
crash recovery must leave unacknowledged events pending. Stable IDs and
cooldowns reduce duplicates, but no local JSON outbox can prove exactly-once
delivery across a process crash and an external provider.

## 4. Deployment runbook recommendation

The production runner should be a dedicated Linux machine or VM with:

- Node.js/pnpm, `bw`, OpenSSH, and only the required helper binaries;
- a dedicated non-root `mise-en-plesk` account;
- SSH host keys enrolled out of band and a restricted known-hosts file;
- read-only checkout/artifact installation;
- a protected state directory with explicit ownership and backups appropriate
  to the value of historical findings (never credentials);
- a separate, protected Hermes configuration/credential provision;
- systemd service/timer units validated with `systemd-analyze verify` before
  activation;
- journald retention/monitoring for service failures and monitor-stale
  findings;
- an operator-owned rotation procedure for Bitwarden sessions, SSH passwords/
  keys, Hermes credentials, and WhatsApp recipient configuration.

The install procedure must be a separately authorized operational change. This
research did not install units, start timers, unlock Bitwarden, connect to
servers, or send a WhatsApp message.

## 5. Architecture work to do next

Use this order for the later architecture pass:

1. **Deepen the transport seam:** make the SSH executor consume typed command
   IDs and return bounded structured observations; keep Plesk CLI, filesystem,
   and WP-CLI adapters behind it.
2. **Separate control-plane adapters:** introduce a typed Plesk metadata port,
   initially backed by CLI. Keep REST/XML implementations optional and
   `GET`/read-packet allowlisted.
3. **Separate scan scheduling from scanning:** make cursor, semaphore, deadline,
   checkpoint, and stale-run semantics testable without SSH.
4. **Make findings the center:** derive reports and notifications from the same
   normalized finding events, with unknown/unavailable states preserved.
5. **Deepen notification delivery:** keep Hermes, webhook, and any future
   channel behind one delivery port; keep outbox/cooldown/recovery semantics
   out of the CLI composition root.
6. **Make deployment a first-class boundary:** separate immutable code,
   runtime state, credentials, and systemd unit configuration; prove the
   installed runner, not only the repository examples.

This is the point where the global `$improve-codebase-architecture` workflow
should be used: after the evidence and operating constraints above are fixed,
review module depth, caller simplicity, dependency direction, and seams before
adding more features. It should produce a small number of deeper modules, not
an application framework.

## 6. Research conclusion

The current direction is sound if the product is defined as a read-only
security monitor, not a Plesk management client. SSH is the right baseline
because it is already the approved access path and is the only one that can
combine Plesk inventory, filesystem evidence, and local WP-CLI execution under
one explicit safety contract. Plesk REST/XML are useful structured supplements
but add privilege, authentication, and mutation-surface concerns. WP-CLI gives
the richest WordPress-specific evidence but must be treated as a fallible
application probe with external-egress annotations. Bitwarden should remain a
runtime credential source, not a cache. Hermes should remain an optional,
redacted, at-least-once notification adapter.

The production gate is therefore operational: provision a trusted always-on
runner, prove the organization-compatible Bitwarden CLI path, enroll SSH host
keys and least-privilege accounts, install the hardened systemd units, and run
one explicitly confirmed Hermes test plus one observed P1/recovery cycle.
Those actions are intentionally outside this research task and require the
operator's authority and real destination configuration.
